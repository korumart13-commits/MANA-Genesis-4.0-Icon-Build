# MANA Genesis 4.0 — Android app compatibility and Google ecosystem plan

Status date: 2026-11-25

## Product requirement

MANA OS is not intended to remain an Android skin or depend on Android as its user-facing operating system. However, it must preserve a compatibility subsystem for existing Android applications. The goal is not to invent a new incompatible app format: ordinary Android APKs must remain installable and runnable through a maintained Android-compatible package/runtime/framework layer (including ART, Package Manager, required APIs, permissions, Binder interfaces and media codecs). This is substantially more than keeping a few codecs.

The Android 16 Compatibility Definition Document states that compatible device implementations must install and run APK files generated by the Android SDK and verify modern APK signature schemes. MANA must not fork the APK format, Android Manifest semantics, DEX bytecode or package signing behavior.

Official reference:
- Android 16 CDD, Application Packaging Compatibility: https://source.android.com/docs/compatibility/16/android-16-cdd
- Android app/device compatibility overview: https://developer.android.com/guide/practices/compatibility
- Android 16 source release announcement: https://android-developers.googleblog.com/2025/06/android-16-is-here.html
- Android 16 platform source refs: https://android.googlesource.com/platform/system/zygote/+refs

## Google Play and Google services: important distinction

AOSP is the open-source Android platform. Google Mobile Services (GMS), Google Play Store and Google Play services are separate proprietary/licensed components and are not included in AOSP by default.

Therefore:
- Keep a dedicated Android-application compatibility layer: Package Manager, ART/Dalvik, required framework APIs, intents, permissions, APK signature verification, Binder contracts and media codecs. MANA's own UI, system services and identity remain MANA-native.
- Do not copy proprietary Google APKs or binaries into MANA images.
- To ship Google Play/GMS preinstalled, the device/product owner must obtain the appropriate Google licensing/partner approval and meet compatibility requirements, including applicable CTS/GTS requirements.
- Without a GMS agreement, MANA can still run compatible Android APKs and can provide a compliant alternative app distribution route, but must not claim that Google Play or native Gmail integration is included. Gmail may be accessed through its supported web experience or standard mail protocols where available; the official Gmail app and Google Play Store depend on licensed Google components and certification.
- Publishing the MANA app on Google Play is a separate developer-account, policy, testing and review process; it does not automatically grant a custom MANA OS permission to bundle GMS.

Official references:
- Google explanation of GMS vs AOSP: https://www.android.com/gms/
- Android compatibility program: https://source.android.com/docs/compatibility/overview
- Google Play target API requirements: https://developer.android.com/google/play/requirements/target-sdk
- Android developer verification: https://developer.android.com/developer-verification

## Android 16 app target

As of the current policy page, from August 31, 2026, new apps and updates submitted to Google Play must target Android 16 (API 36) or higher, with listed platform-specific exceptions. MANA app build should therefore use compileSdk 36 / targetSdk 36 when the selected Android Gradle Plugin and dependency stack support it, and CI must test Android 16 behavior changes. Do not silently force a target SDK change without compiling and testing the dependency graph.

## MANA as default Home

The Android app should declare MAIN/LAUNCHER and MAIN/HOME + DEFAULT intent filters for ManaHomeActivity. The user must be able to select MANA in Android's Home app settings. On ordinary Android this is a user-selected launcher app, not a privileged system app.

When MANA is later integrated into a licensed AOSP product:
- provide a real Soong module and include it in PRODUCT_PACKAGES;
- set the default HOME role using supported product configuration;
- retain user ability to change the default launcher unless product policy explicitly and lawfully requires otherwise;
- do not request signature permissions unless MANA is signed with the authorized platform key and the permission is genuinely needed.

## Required platform services

MANA must use standard Android mechanisms:
- PackageManager and LauncherApps for installed app discovery/launch, subject to package visibility;
- Intent/RoleManager for user-mediated default roles;
- Runtime permissions and AppOps for sensitive capabilities;
- Storage Access Framework for user-selected files;
- MediaStore for shared media;
- NotificationListenerService / CallScreeningService only after explicit user enablement and role grants;
- WorkManager/JobScheduler/foreground service types for background work within Android limits;
- Android Keystore for app secrets; never embed provider API keys in the APK.

## Architecture rule

MANA is a system-like user experience, but app-level Kotlin classes are not a Linux kernel and do not grant system privileges. Preserve a clean boundary:
1. MANA application and local AI runtime.
2. Android framework integration through public APIs.
3. AOSP product/Soong integration.
4. OEM-specific device tree, kernel, vendor interface and firmware.

Do not claim layer 3 or 4 is complete merely because layer 1 builds.

## Google Drive access note

Gmail access is not Google Drive access. The current connected Gmail integration can search/send email; Google Drive connector availability is disabled by the workspace administrator, so no private Drive/Docs/Android files were inspected. Only public official Android/AOSP sources were used for this plan. The owner can provide public links or attach files if private Drive material is required.

## Acceptance gates

- [ ] Build app with Android API 36 toolchain and compatible dependencies.
- [ ] Test install, upgrade, uninstall, signing, deep links, app links, permissions and package visibility.
- [ ] Verify third-party APK install and run without changing APK/DEX formats.
- [ ] Verify default launcher selection and fallback to another launcher.
- [ ] Run Android 16 compatibility tests and CTS/VTS for a complete OS product.
- [ ] Keep GMS out of images until written authorization/licensing and compatibility requirements are met.
- [ ] Confirm Google Play app listing/review separately from OS/GMS licensing.
